# CLAUDE.md — RHDH Operator

This file provides context for AI agents working on this repository.

## Project Overview

This is the **Red Hat Developer Hub (RHDH) Operator**, a Kubernetes operator
for deploying and managing [Backstage](https://backstage.io) instances on
Kubernetes and OpenShift. It is built with
[kubebuilder](https://book.kubebuilder.io) and
[operator-sdk](https://sdk.operatorframework.io).

The operator manages a `Backstage` custom resource (CR) in the
`rhdh.redhat.com` API group and reconciles it into a set of Kubernetes
resources (Deployment/StatefulSet, Service, ConfigMaps, Secrets, Routes,
PVCs, etc.) that make up a running Backstage instance with an optional
local PostgreSQL database.

**Key features:**

- Configuration profiles (`rhdh`, `backstage.io`, `external`) that
  customize default resources, image tags, OLM bundle metadata, and
  channels.
- Three-layer configuration model: operator-level defaults, raw runtime
  config (ConfigMap), and CR-level spec fields.
- Dynamic plugins support with operator-side processing
  (`OPERATOR_DP_PROCESSING=true` by default), including `ref://` and
  `{{inherit}}` URL resolution and plugin dependency management.
- Platform-aware patches (`.k8s` / `.ocp` extensions) applied
  automatically based on the detected platform.
- External config watching — the controller watches ConfigMaps and
  Secrets referenced by a Backstage CR and refreshes the workload
  when they change.

**Go module:** `github.com/redhat-developer/rhdh-operator`

## Build and Development Commands

All commands use `make`. The default profile is `rhdh`; override with
`PROFILE=<name>`.

| Command | Description |
|---|---|
| `make build` | Build the operator binary (`bin/manager`) |
| `make test` | Run unit tests with envtest (includes `manifests generate fmt vet`) |
| `make integration-test` | Run integration tests with Ginkgo |
| `make test-e2e` | Run end-to-end tests (requires a real cluster) |
| `make lint` | Run golangci-lint (`$(GOLANGCI_LINT) run --timeout 15m`) |
| `make fmt` | Format Go code with goimports |
| `make vet` | Run `go vet ./...` |
| `make manifests` | Generate CRD, RBAC, and webhook manifests |
| `make generate` | Generate DeepCopy methods |
| `make bundle` | Generate OLM bundle for the current profile |
| `make image-build` | Build the operator container image |
| `make deploy` | Deploy the operator to a cluster |
| `make install` | Install CRDs into the cluster |
| `make local-dynamic-plugins` | Extract default dynamic-plugins config from catalog-index image (run once for `rhdh` profile) |
| `make gosec` | Run gosec security scanner |

### Prerequisites

- Go 1.26.0+
- For local testing: `kubectl` and a cluster (minikube, kind, or remote)
- For `rhdh` profile local testing: run `make local-dynamic-plugins`
  first (requires `skopeo`)

## Test Structure

- **Unit tests:** `go test` via `make test`. Source packages are in
  `pkg/model/`, `pkg/utils/`, and `internal/controller/`. Tests use
  envtest (kubebuilder test environment) and are co-located with source
  files (`*_test.go`).
- **Integration tests:** `integration_tests/` directory, run with
  Ginkgo via `make integration-test`. Can use envtest or a real cluster
  (`USE_EXISTING_CLUSTER=true`).
- **End-to-end tests:** `tests/e2e/`, run with Ginkgo via
  `make test-e2e`. Require a real cluster with the operator deployed.
- **Test data:** `integration_tests/testdata/` and
  `pkg/model/testdata/` contain fixture manifests.

When writing tests, follow the existing patterns:
- Use Ginkgo/Gomega for integration and e2e tests.
- Use standard Go `testing` package or `testify` for unit tests.
- Place test data in a `testdata/` subdirectory.

## Architecture Notes

### Reconciliation Flow

1. The `BackstageReconciler` in `internal/controller/` watches
   `Backstage` CRs and referenced ConfigMaps/Secrets.
2. The spec preprocessor resolves dynamic plugin references (`ref://`,
   `{{inherit}}`), merges default and user-provided plugin configs.
3. The `pkg/model` package builds the desired runtime object model
   (Deployment, Services, DB resources, etc.) from the three config
   layers.
4. The controller applies objects to the cluster using server-side apply
   with the `backstage-controller` field manager.
5. Status is updated with `Deployed`, `DeployFailed`,
   `DeployInProgress`, or `Idled` conditions.

### Profile System

Profiles live under `config/profile/<name>/` and
`config/manifests/<name>/`. Each profile provides:
- Default-config directory with Kubernetes manifest templates
- Kustomize overlays for deployment
- OLM bundle metadata

The `PROFILE` variable (`rhdh` by default) selects which profile is
used for `make test`, `make deploy`, `make bundle`, etc.

### Current API Version

The current CRD API is **v1alpha5** (`rhdh.redhat.com/v1alpha5`).
Earlier versions (v1alpha1 through v1alpha4) are retained for
conversion support.
